# Documentation Generator — Submission

This document walks through the design, build, review, and automation of a documentation generator for this repository (a React + Vite personal site). It covers: what the generator does, the project's CLAUDE.md, the first-version output and a critical review of it, the Plan Mode plan used for the v2 rewrite, the custom slash command and hook that automate it, the permissions guardrails put around that automation, and one full end-to-end automated run.

---

## (a) Short description of the generator

`scripts/generate-docs.js` (with logic split across `scripts/docgen/parse.js`, `graph.js`, and `render.js`) reads every `.js`/`.jsx` file under `src/` and writes markdown documentation into `docs/`: one file per source file plus a `docs/README.md` index. It is regex-based, not an AST parser — deliberately kept dependency-free and simple for this codebase's plain function-component style.

Per file, it reports:
- **Description** — from a leading `/** ... */` block, or a fallback derived from the JSX root element's `id` attribute.
- **Imports** and, via a reachability analysis from `src/main.jsx`, an **"Imported by"** list.
- **Exports vs. internal helpers** — components split into what the file actually exposes vs. private, non-exported helpers.
- **Local data constants** — top-level `UPPER_CASE` arrays/objects.
- **Orphan detection** — a `⚠ Not imported anywhere` banner (and index-table marker) for any file unreachable from the app's entry point, so dead code is flagged automatically instead of documented with false authority.

It runs via `npm run docs`, a `/generate-docs` slash command, and automatically after any edit under `src/` via a `PostToolUse` hook (see sections e–g).

## Conventions

- Function components only (`export default function Name() {}`); no class components, no TypeScript, no router.
- Page sections are tabs held in `App.jsx`'s local `useState`, not routes.
- No CMS/API/markdown: page content is hardcoded JS arrays/objects inside the component that renders it (e.g. `About.jsx`'s `INTERESTS`, `SKILL_GROUPS`, `NEWS`).
- Styling is Tailwind utility classes only — no CSS modules, no styled-components. Custom tokens (brand color, font) live in `tailwind.config.js`.
- `src/components/Hero.jsx`, `Research.jsx`, `News.jsx`, `Skills.jsx` are orphaned — not imported anywhere. Don't assume edits to them affect the live site.

## Documentation

`docs/` is generated by `npm run docs` (`scripts/generate-docs.js` + `scripts/docgen/`) from `src/**/*.{js,jsx}`. Never hand-edit anything under `docs/` — edit the source file and re-run the generator instead. Re-run it after adding a component, renaming one, changing its props, or changing what imports what.

Per file it reports: description (from a leading `/** ... */` block, else a fallback based on the JSX root element's `id`), imports, **exports vs. internal (non-exported) helpers** as separate sections, local `UPPER_CASE` data constants, and — via `scripts/docgen/graph.js` walking the import graph from `src/main.jsx` — an **"Imported by" list** plus a **`⚠ Not imported anywhere` banner** (and an `⚠` in the index table) for files unreachable from the entry point. This is how `Hero.jsx`, `Research.jsx`, `News.jsx`, `Skills.jsx` get flagged as dead code automatically instead of relying on this doc to say so.

The generator is regex-based (`scripts/docgen/parse.js`), not an AST parser, so write source in the forms it understands: a component is `export default function Name(props) {}`, `export function Name(props) {}`, `export const Name = (props) => {}`, or a non-exported local helper as either `function Name(props) {}` or `const Name = (props) => {}`. Destructured props (`{ a, b }`) are rendered as such in signatures, not as positional args.

## Deployment

`.github/workflows/deploy.yml` builds and deploys on every push to `main` (or manual `workflow_dispatch`): `npm ci` → `npm run build` → upload `dist/` → `actions/deploy-pages`. The workflow sets `concurrency: {group: pages, cancel-in-progress: true}` to prevent overlapping/queued Pages deployments — keep this if editing the workflow. There is no CNAME; the site serves at the default `ajoydey00001.github.io`.

### Critique

**What's accurate:** imports, component names, and prop lists are all factually correct. Every destructured prop list matches the source exactly. Data-constant detection works well (`SOCIALS`, `PROJECTS`, `TAG_COLORS`, etc. all correctly picked up). Zero-component and zero-import files render sensibly rather than breaking.

**Where it's vague:** every "Description" is `—` (no JSDoc exists anywhere in the codebase, so the generator has nothing to summarize). Signature format is misleading: `SectionHeader(title, subtitle)` reads like positional args, but the real signature is `SectionHeader({ title, subtitle })` — destructured object props. "Local data constants" lists bare names with no shape.

**Confident hallucinations (the important finding):** the generator presents every file with identical authority regardless of whether it's actually live code. `Research.jsx` and `Publications.jsx` read almost identically in the v1 docs, but only `Publications` is wired into `App.jsx`; `Research.jsx`, `Hero.jsx`, `News.jsx`, `Skills.jsx` are never imported anywhere — and nothing in the v1 output says so. A reader relying only on `docs/` would reasonably conclude all 14 files ship. Similarly, `CV.jsx`'s index row lists `CV, TimelineItem` as if both were part of the module's public surface, but `TimelineItem` is an unexported local helper. These aren't fabricated facts, but they create a false impression of uniformity and completeness.

**Improvements identified (priority order):**
1. Cross-reference the import graph from `src/main.jsx` and mark unreachable files/components — highest value, since the orphan-file problem is real and was invisible.
2. Mark exported vs. non-exported symbols separately.
3. Fix signature rendering to show `{ title, subtitle }` when destructured, not positional args.
4. Support arrow-function local helpers (`const Foo = () => {}`) — only `function Foo(...)` declarations were caught.
5. Infer a fallback description from the JSX root element's `id`/section role when no JSDoc exists.
6. Surface the calling context (which parent renders this) — implemented generically as the graph's reverse "Imported by" edges rather than a brittle, App.jsx-specific heuristic.

All six items were carried into the v2 rewrite (see Plan Mode plan below); items 1–5 were implemented, item 6 was generalized as described.

## (d) Plan Mode plan

Written via `EnterPlanMode` → `ExitPlanMode`, approved by the user before any implementation:

```markdown
# Plan: Multi-file improvement to the docs generator

## Context

`scripts/generate-docs.js` (v1) was built and reviewed earlier this session. The critical review found it's accurate on signatures/imports/data-constants, but has one serious problem and a few smaller ones:

- **Confident hallucination by omission**: dead/orphaned components (`Hero.jsx`, `Research.jsx`, `News.jsx`, `Skills.jsx` — confirmed unreferenced by `App.jsx`) are documented with identical authority to live ones. Nothing in the output signals they're unreachable.
- Exported symbols and unexported local helpers (e.g. `CV.jsx`'s `TimelineItem`) are listed identically, implying a public API that doesn't exist.
- Signatures render destructured props as positional args (`SectionHeader(title, subtitle)` instead of `SectionHeader({ title, subtitle })`), which is misleading if read literally.
- Arrow-function local helpers (`const Foo = () => {}`) are silently invisible to the extractor — only `function Foo() {}` declarations are caught outside the export patterns.
- No file gets a description unless it has a top-of-file JSDoc block (none currently exist), so the index is all `—`.

This plan fixes the orphan-detection gap (highest value) plus the three cheap, mechanical fixes, and turns the single-file script into a small multi-module design so parsing, graph analysis, and rendering are independently readable/changeable. It intentionally stays regex-based (no new dependency, no AST parser) and keeps scope to `src/**/*.{js,jsx}`, consistent with v1.

## File layout

Split `scripts/generate-docs.js` into:

- **`scripts/docgen/parse.js`** — per-file extraction (moved from the current script, extended):
  - `extractComponents` gains a third regex for non-exported arrow-function helpers (`(?:^|\n)\s*const\s+(\w+)\s*=\s*\(([^)]*)\)\s*=>`), and now tags each match with `{ name, props, exported }` — `exported: true` for the three `export ...` patterns, `false` for the two local-helper patterns (function-declaration and arrow).
  - `parseProps` returns `{ names, destructured }` instead of a bare array, so rendering knows whether to print `{ a, b }` or `(a, b)`.
  - New `extractSectionId(source)` — cheap regex for the first `id="..."` literal in the file, used as a fallback description hook.
  - `extractFileDescription`, `extractImports`, `extractDataConstants` move here unchanged.
- **`scripts/docgen/graph.js`** (new) — given the full file list and each file's parsed imports, resolve relative import specifiers to absolute paths, build a directed graph, do reachability from `src/main.jsx`, and produce per-file `{ reachable: bool, importedBy: string[] }`. This is what turns "imports" (already extracted) into "is this file actually alive."
- **`scripts/docgen/render.js`** (new) — takes one file's parsed data + its graph info and produces the per-file markdown (adds a `⚠ Not imported anywhere` banner when `!reachable`, splits "Exports" vs "Internal helpers" sections, prints `{ a, b }`-style signatures for destructured props, adds an "Imported by" line). Also renders the index table (add an "Orphan" column, `⚠` marker).
- **`scripts/generate-docs.js`** — thin orchestrator: walk `src/`, call `parse` per file, call `graph`, call `render` per file + index, write to `docs/`. Keeps the existing `npm run docs` entry point and output location so nothing else has to change.

No new dependencies; still ESM (`type: module` already set in `package.json`).

## What's explicitly out of scope for this pass

- No AST parser (babel/acorn) — regex stays the good-enough tool for this codebase's plain function-component style.
- No hardcoded "rendered when activeTab === X" narrative parsing (too brittle/one-off to `App.jsx`'s specific pattern) — the generic "Imported by" reverse-edge from the graph covers the same need (which parent renders this) more robustly.
- No test framework addition — repo has none today; verification is manual (see below), matching how v1 was verified.

## Verification

1. `npm run docs` — regenerate `docs/`.
2. Read `docs/src/components/Research.jsx.md` (or `Hero.jsx`/`News.jsx`/`Skills.jsx`) and confirm the `⚠ Not imported anywhere` banner appears; confirm `docs/src/components/About.jsx.md` (reachable) does not have it.
3. Read `docs/src/components/CV.jsx.md` and confirm `TimelineItem` is listed under "Internal helpers" (not "Exports"), and that `docs/src/components/SectionHeader.jsx.md` shows the signature as `SectionHeader({ title, subtitle })`.
4. Confirm `docs/README.md`'s table has an orphan indicator and that it's blank/absent for live files.
5. `npm run build` — confirm the unrelated Vite build still passes (sanity check nothing outside `scripts/` was touched).
6. Update the "Documentation" section of `CLAUDE.md` to mention orphan-detection, exported/helper separation, and arrow-function support, keeping it in sync per the established habit from the v1 build.
```

All six verification steps were run after implementation and passed (see section g for one live example).

## (e) Custom slash command and hook configuration

### Slash command — `.claude/commands/generate-docs.md`

```markdown
---
description: Regenerate docs/ from src/ using the project's documentation generator
---

Run this project's documentation workflow in one step:

1. Run `npm run docs` from the repository root. This executes `scripts/generate-docs.js`, which walks `src/**/*.{js,jsx}`, analyzes the import graph via `scripts/docgen/graph.js`, and writes markdown into `docs/` via `scripts/docgen/render.js`.
2. Report how many files were generated (from the script's console output).
3. Read `docs/README.md` and tell the user which files, if any, are flagged `⚠` (orphaned / not imported anywhere from `src/main.jsx`), since that's the signal most likely to need their attention.

Do not hand-edit anything under `docs/` — it is entirely regenerated by this command.
```

Invoked as `/generate-docs` — the manual trigger.

### Hook — `.claude/settings.json`

```json
{
  "permissions": {
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force*)",
      "Bash(git push -f*)",
      "Edit(docs/*)",
      "Write(docs/*)"
    ],
    "ask": [
      "Edit(.claude/settings.json)",
      "Write(.claude/settings.json)",
      "Edit(.claude/settings.local.json)",
      "Write(.claude/settings.local.json)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path // empty' | { read -r f; case \"$f\" in */src/*) (cd \"${CLAUDE_PROJECT_DIR:-.}\" && npm run docs --silent) ;; esac; } || true",
            "timeout": 30,
            "statusMessage": "Regenerating docs/ from src/..."
          }
        ]
      }
    ]
  }
}
```

A `PostToolUse` hook on the `Write|Edit` matcher: it reads the edited file's path from the hook's stdin JSON, and if the path is under `src/`, runs `npm run docs`. This is the automatic trigger — no manual step required after editing source.

**Verification performed before trusting it:**
1. Pipe-tested the raw command with synthetic stdin JSON: a `src/` path triggered regeneration, a non-`src/` path (`CLAUDE.md`) correctly did not.
2. Schema-validated with `jq -e '.hooks.PostToolUse[] | select(.matcher == "Write|Edit") | .hooks[] | select(.type == "command") | .command'` — exit 0.
3. Proved it fires for real: deleted `docs/`, made an actual `Edit` tool call to `src/main.jsx` (a throwaway `// hook-fire-test` comment, immediately reverted), and confirmed `docs/README.md` reappeared automatically with no manual `npm run docs` call.
4. Confirmed `npm run build` still passes afterward.

## (f) Permissions notes

Guardrails were added to `.claude/settings.json` (team-wide, committed) alongside the hook. The user explicitly chose to leave the pre-existing `Bash(npm run *)` wildcard in `.claude/settings.local.json` untouched, and only add new deny/ask rules for operations this automation has no legitimate reason to perform:

| Rule | Type | Reasoning |
|---|---|---|
| `Edit(docs/*)`, `Write(docs/*)` | deny | Enforces the `CLAUDE.md` rule "never hand-edit `docs/`" as a technical control, not just a written convention — forces all changes through the generator. |
| `Bash(rm -rf *)` | deny | The docs workflow never needs recursive force-delete; blocks it from ever being an unreviewed side effect. |
| `Bash(git push --force*)`, `Bash(git push -f*)` | deny | Nothing about doc generation should ever need a history rewrite. |
| `Edit`/`Write` on `.claude/settings.json` and `.claude/settings.local.json` | ask | Guards the guardrails — the automation's own config always requires explicit confirmation to change, so it can't silently expand its own permissions. |

**Honest finding from testing, not assumption:** the `docs/*` deny rule was tested for real — by editing `docs/README.md` with the `Edit` tool (safe to test, since it's regenerable and not destructive). **The edit went through instead of being blocked.** Unlike the hook (confirmed to re-read live, see section e), permission rules appear to be snapshotted at session start rather than re-evaluated per call, so a mid-session change to `settings.json` isn't enforced until the session reloads/restarts. The test pollution was cleaned up immediately via `npm run docs`. The rule is syntactically valid (`jq -e` confirmed) and expected to take effect on the next session, but this document reports the gap as observed rather than assuming the rule works because the JSON was correct.
